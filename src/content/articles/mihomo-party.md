Mihomo Party 是一款基于 Mihomo 内核的桌面图形客户端，干的活和 Clash Verge Rev 一样：导入订阅、选节点、开关系统代理和 TUN。先说结论：两者底层是同一类内核，能力差别不大，差别主要在界面取向和使用习惯，选哪个更像选输入法，试一个顺手的就行。下面把名词、特点、选择方法和下载注意事项一次讲清。

## Mihomo、Clash Meta、Mihomo内核：几个名字是什么关系

这几个词在教程里经常混着用，先对照一遍：

| 名字 | 它是什么 | 你需要单独下载吗 |
|---|---|---|
| Clash（原版内核） | 早期的代理内核，已停止更新 | 不需要，也不建议 |
| Clash Meta | 在原版基础上扩展协议和功能的分支，后来更名为 Mihomo | 老教程里的叫法，指向同一条路线 |
| Mihomo | 现在持续维护的内核，本身没有图形界面 | 一般不需要，客户端自带 |
| Mihomo内核 | 对上面这个内核的泛称 | 同上 |
| 图形客户端 | 套在内核外面的操作界面 | 需要，二选一或多选 |

Mihomo 本身是个读 YAML 配置的命令行程序，没有按钮，客户端把它包装成了窗口。它支持的协议很全，常见的 Shadowsocks、VMess、VLESS、Trojan、Hysteria2 等都在列，具体哪个版本支持哪个协议，以内核官方说明为准。想查文档或看更新说明，可以去 [Mihomo 内核仓库](https://github.com/MetaCubeX/mihomo)，但那是给查资料用的，普通用户不必去下载内核文件替换。

## 它有什么特点：覆写、跨平台和界面取向

下面这些来自项目自己的介绍，界面文案和功能会随版本变化，以实际安装后的页面为准：

- **跨平台**：通常提供 Windows、macOS、Linux 的构建，具体以 Release 页面实际列出的文件为准；
- **界面框架不同**：据项目说明，这款客户端基于 Electron 开发，而 Clash Verge Rev 走的是 Tauri 路线。一般来说 Electron 应用自带完整的浏览器组件，安装包体积会大一些，换来的是对系统网页组件的依赖更少；
- **覆写**：提供类似“覆写”的功能，可以在不改动订阅原文的前提下叠加自己的设置，订阅更新时不会被冲掉；
- **常规能力**：规则、全局、直连三种模式，系统代理，TUN，以及连接与日志的查看，这些是 Mihomo 系客户端的标配；
- **订阅管理**：支持多个订阅切换，也可以设置自动更新的时间间隔。

有一件事要提前交代：开源项目的名称、仓库归属和维护状态都可能调整。打开下载链接后，以仓库页面显示的名字和说明为准，并看一眼最近有没有更新记录。长期没人维护的客户端，不要新装。

## Mihomo Party 和 Clash Verge Rev 怎么选

| 维度 | Clash Verge Rev | 这款客户端 |
|---|---|---|
| 内核 | Mihomo | Mihomo |
| 订阅格式 | 吃 Clash 或 Mihomo 能解析的订阅 | 相同 |
| 界面框架（据项目说明） | Tauri | Electron |
| 自定义配置 | 有类似合并、脚本的增强功能 | 有类似覆写的功能 |
| 适合谁 | 想先跑通、对着教程一步步做的新手 | 想换个界面，或前者在你机器上不顺手的人 |

选择路径可以这么走：

1. **第一次接触**：先从 Clash Verge Rev 开始，下载与安装包挑选见 [Clash Verge下载](/clients/clash-verge/)，跑通以后再决定要不要换；
2. **前一个用着别扭、或者想玩覆写**：试这款客户端；
3. **两个都想试**：可以，但同一时间只开一个，否则两边抢系统代理和 TUN。换用前先在原客户端里关掉系统代理再退出；
4. **不想被 Clash 配置格式绑定**：看看 [Sing-box教程](/clients/sing-box/)，那是另一套思路，门槛也更高。

没有谁全面压过谁，吵“哪个更好”基本是浪费时间。能顺利导入订阅、能找到可跟着做的教程、项目仍在更新，这三条比界面好不好看重要得多。

## 订阅与规则：导入之后怎么用

这部分操作和其他 Mihomo 系客户端大同小异，按顺序做：

1. 找到类似“订阅”或“配置”的页面，粘贴机场给的订阅链接并导入。订阅要是 Mihomo 能解析的格式，机场只给通用格式时需要转换，转换的风险见 [订阅转换](/tutorials/dingyue-zhuanhuan/)；
2. 模式先选“规则”，打开系统代理，用浏览器验证能否正常访问；
3. 想自己调分流，先把规则集、策略组的概念弄清楚，入门见 [分流规则](/tutorials/mihomo-fenliu-guize/)；
4. 自己的修改放进覆写，不要直接改订阅生成的配置文件，否则下次更新订阅就被覆盖了；
5. 订阅更新间隔不用太勤，参考 [订阅更新频率](/tutorials/dingyue-gengxin-pinlv/)。

关于覆写，有两点提醒。第一，怎么在覆写里追加规则，各客户端的写法并不统一，有的用专门的前置规则字段，具体以项目文档为准，不要照搬别的客户端的教程。第二，YAML 靠缩进表达层级，缩进必须用空格，写错一格就可能整份配置报错，出现问题时先停用覆写，确认订阅本身正常，再逐条加回去。

订阅链接等同于账号凭证，不要发群、不要放进截图，泄露后的处理见 [机场订阅链接安全](/knowledge/dingyue-lianjie-anquan/)。

## 官方渠道下载：只走仓库 Release 页面

下载入口只认官方仓库的 [Mihomo Party Release 页面](https://github.com/mihomo-party-org/mihomo-party/releases)。核对仓库路径，注意名字相近的仿冒仓库；安装包在页面的 Assets（资源）列表里，常见安装版和便携版两种形态，以实际列出的文件为准。

- Windows 和 Mac 要分清 x64 与 arm64 的架构，确认方法与文件名对照见前面提到的 Clash Verge 那篇，这里不重复；
- 不要用搜索引擎广告位里的“官网”、网盘分享或群里转发的安装包，也不要碰标着“破解”“集成”“去限制”的整合包；
- Mac 提示无法验证开发者时，放行步骤见 [Mac客户端教程](/clients/mac-jichang-kehuduan/)，Windows 上的权限、杀毒软件与系统代理问题见 [Windows客户端教程](/clients/windows-jichang-kehuduan/)。

## 五种处境怎么选：什么时候留在 Mihomo Party，什么时候换个客户端

下面五种处境很常见，按“如果你是……就……，因为……”对号入座。

- **如果你刚从 Clash for Windows 迁过来，手里有一份自己调过的规则**：先在新客户端里导入订阅跑通，再把自己的规则一条条搬进覆写，不要把旧配置文件整份复制过来覆盖。原因是旧配置的字段和写法，未必跟得上 Mihomo 内核现在的写法，整份替换后出了错，你很难判断是哪一条惹的祸。逐条加回去，出错时只需要回退最后一条；
- **如果你只想让浏览器能正常访问，不想碰任何设置**：订阅导入后用规则模式加系统代理，覆写和 TUN 都先不动。配置最简单，出问题时可疑对象也最少。过一两周，真遇到不够用的场景，再回来研究其他功能；
- **如果你有两台电脑，想两边都用**：两台电脑各自安装、各自导入同一条订阅，客户端之间的配置不会自动同步。要留意的是机场套餐通常对同时在线的设备数有限制，具体规则以机场的套餐说明为准，选套餐之前可以先看 [机场怎么选](/guides/jichang-zenme-xuan/)；
- **如果你经常改规则，又不想订阅一更新改动就没了**：所有改动都放进覆写，每次只改一处，保存后用浏览器验证，再改下一处。顺手在笔记里记一行“改了什么、为什么改”，几周以后你会感谢自己。订阅链接本身别写进这份笔记，笔记同样可能被别人看到；
- **如果某个节点在这个客户端里连不上，在别的设备上却正常**：先查这个节点用的协议，客户端自带的内核是否支持，再查订阅格式有没有被正确解析，协议之间的区别见 [VLESS、Trojan、Hysteria2 的区别](/knowledge/vless-trojan-hysteria2-bijiao/)。拿不准时，换一款同样基于 Mihomo 内核的客户端对照一下，能帮你判断问题出在客户端，还是订阅或节点本身。

## 装好以后的自查清单：十一条，逐项勾完再日常使用

这份清单不追求一次勾满。建议装好当天勾一遍，之后每次升级客户端、换电脑，再勾一遍。没勾上的那几条，就是你下一步要查的地方。

- [ ] 安装包来自官方仓库的 Release 页面，仓库路径核对过，不是名字相近的仿冒仓库；
- [ ] Windows 的系统类型或 Mac 的芯片已确认，安装包文件名里的 x64、arm64 标记没有选反；
- [ ] 订阅已导入，节点列表不是空的，订阅备注改成了自己认得的名字；
- [ ] 当前模式是“规则”，而不是全局；
- [ ] 系统代理已打开，浏览器能正常访问；
- [ ] 电脑上没有另一个代理客户端同时开着系统代理或 TUN；
- [ ] 自己的修改都放在覆写里，没有直接编辑订阅生成的配置文件；
- [ ] 覆写里的缩进用的是空格，改完能正常保存，配置没有报错；
- [ ] 订阅自动更新的间隔已设成合理值，参考 [订阅更新频率](/tutorials/dingyue-gengxin-pinlv/)；
- [ ] 订阅链接没有出现在截图、聊天记录或公开笔记里；
- [ ] 需要 TUN 的话，已确认权限和服务组件就绪，并且知道怎么把它关掉。

## 进阶：规则自上而下匹配，覆写追加的规则放哪里才会生效

覆写之所以容易写错，根源是没搞清楚 Mihomo 内核处理规则的方式。这一节往深里讲一层，细节以内核官方文档和你所用客户端的说明为准。

**规则是自上而下匹配的，先命中的先生效。** 内核拿到一个连接请求，会从规则列表的第一条开始比对，命中了就按这一条指定的出口处理，后面的规则不再看。所以规则的顺序本身就是配置的一部分。订阅里的规则列表最后通常有一条兜底规则，写成 MATCH 之类，意思是“前面都没命中的，统统走这个出口”。下面是结构示意，不能直接照抄：

```yaml
rules:
  - DOMAIN-SUFFIX,example.com,DIRECT
  - GEOIP,CN,DIRECT
  - MATCH,节点选择
```

示例里的 example.com 是占位域名，“节点选择”是示意的策略组名，真实的组名以你订阅里实际存在的为准。

由此推出一个很实用的结论：**你自己追加的规则，要放在兜底规则之前，也要放在会提前命中它的宽泛规则之前。** 放到 MATCH 后面，永远轮不到它生效；放到一条覆盖面很大的规则后面，同样可能被抢先命中。这就是很多客户端的覆写功能专门提供“前置”一类写法的原因，目的是把你的规则插到订阅规则前面。具体字段名各客户端并不统一，以项目文档为准。

**策略组决定“同一条规则命中后选哪个出口”。** 常见的有三类：手动选择型，由你自己在界面里点；自动测试型，按定时测试的结果自动挑一个；故障转移型，当前出口不可用时切到下一个。它们的区别在于“谁来选”，不在于“选得好不好”。自动测试依据的是握手类指标，数字小不等于下载快，这和客户端里显示的延迟数字是同一个道理。

**这套思路什么时候不适用？** 如果你用的是全局模式，规则列表被整体绕开，所有流量都走所选的那一个出口，覆写里的规则自然看不出效果，两种模式的区别见 [全局模式与规则模式](/glossary/global-vs-rule-mode/)。另外，订阅一旦定时更新并重新生成配置，没放进覆写的手动改动就会被冲掉。遇到“我明明加了规则却没效果”，按这个顺序查：当前是不是规则模式，规则的位置是不是在兜底规则之前，有没有被前面的宽泛规则抢先命中。规则的入门概念和更多写法，见 [分流规则](/tutorials/mihomo-fenliu-guize/)。

## 今天就能做的三件事

1. 先搞清自己的系统架构，从官方仓库拿对应的安装包，装好以后别急着折腾覆写；
2. 导入订阅、规则模式加系统代理，先让最基本的访问跑通一次；
3. 客户端只是工具，订阅才是消耗品。想比较不同机场的资料，去 [机场推荐排行榜](/rankings/) 对照着看，别让客户端的选择替你决定买哪家。

软件界面、功能与仓库归属会随版本和维护者调整，一切以项目官方说明为准。使用代理服务请遵守所在地法律法规，机场牛不提供法律意见。
