faqs:
  - q: 哪种测速工具更适合新手？
    a: 新手先用客户端内置的延迟测试筛掉不通的节点，再用一个网页测速页面看大致带宽，最后用你真实要访问的网站、视频或下载做验证。没有哪一种工具能单独回答所有问题，把三者结合起来，比纠结选哪一个更可靠。
  - q: 客户端延迟测试显示超时，是不是说明节点坏了？
    a: 不一定。超时可能是节点真的失效，也可能是测试地址在当前网络下访问不通、系统代理设置循环、订阅过期或本地网络波动。建议换一个测试地址再测一次，并换个时间重试，多个时间点都超时才更像节点本身的问题。
  - q: 测速会消耗多少流量，要不要在意？
    a: 要在意。网页测速和下载测试都会实际产生流量，并且按节点的流量倍率扣减，套餐流量不多的话，反复测速本身就会消耗不少额度。建议缩短测试时长、控制次数，把大流量测试集中在你真正想验证的几个节点上。
  - q: 一天里什么时候测速才有代表性？
    a: 至少覆盖两类时段：网络相对空闲的时候，以及你日常实际使用最集中的晚间高峰。每个时段重复测几次，并且在不同的日子里再测，一次的结果只能算快照。同时记录网络类型和测试目标，才方便前后对比。
  - q: 测速结果可以拿给客服当依据吗？
    a: 可以，但要写清楚测试条件，包括时间、设备、网络类型、节点名称、测试方法和多次结果，附上截图时注意遮挡订阅链接。有条件的反馈比一句慢得离谱更容易得到处理，也方便你之后核对服务商是否真的做了调整。
  - q: 测速时需要关闭其他软件吗？
    a: 建议关闭或暂停。后台下载、云盘同步、在线视频和系统更新都会占用带宽和处理器，把结果拉低，让你误以为是节点的问题。有条件的话改用有线连接，并在记录表里加一列“是否有干扰”，前后对比时才知道差异来自节点还是来自本机。

机场测速工具怎么用，先给结论：**客户端里那个延迟数字只能当"通不通"的参考，不能当"快不快"的依据。** 靠谱的做法是 5 类工具配合着用，再把测试条件控制住：同一时段、同一节点、重复多次、对着真实场景看。这篇文章把 5 类工具各自测什么、不能测什么讲清楚，再教你设计一次能复盘的测试，避开最常见的误读。

## 机场测速工具有哪几类：先看每类测的是什么

选机场测速工具之前，先上总表。这 5 类工具的常见实现大多可以免费使用，具体功能和限制以各工具自己的说明为准：

| 类型 | 测的是什么 | 好处 | 局限 |
|---|---|---|---|
| 客户端内置延迟测试 | 通过节点发一个很小的请求，看完成耗时 | 快，能一次性筛掉不通的节点 | 不反映带宽，也不反映晚高峰 |
| 网页测速 | 在浏览器里跑下载、上传，得到带宽估算 | 直观，不用装软件 | 受测速服务器位置和浏览器影响，会消耗流量 |
| 命令行工具 | ping、curl 等，按需测延迟或下载耗时 | 可重复、可脚本化 | 门槛稍高，输出需要自己解读 |
| 路由追踪 | 数据包经过哪些跳点、哪一段延迟突增 | 能帮你定位"慢在哪一段" | 走的是你本机直连网络，需要谨慎解读 |
| IP 质量检测 | 出口 IP 的归属、类型、DNS 是否泄漏 | 能核对宣传的出口信息 | 不测速度，只测出口是否合适 |

### 客户端内置延迟测试：只用来筛节点

多数客户端都有一个"测试延迟"的按钮：它通过节点去请求一个很小的测试地址，把完成一次请求的耗时显示出来。有的客户端还把"只测端口握手"和"经节点发真实请求"分成两个选项，哪个是哪个，以客户端界面和说明为准。它最适合做的事：刚导入订阅时，快速知道哪些节点不通，把明显超时的先排除。

### 网页测速：看带宽的大致量级

网页测速页面通过下载和上传一段数据来估算带宽。用它的时候要注意三点：

- 开着代理时，测的是"你到节点、再到测速服务器"这一整条路，测速服务器离出口越远，结果越受影响；
- 页面通常用多条并发连接，日常单个下载未必能跑到同样的数值；
- 测试会实打实消耗流量，按倍率扣，别连续狂点。

### 命令行工具：适合想要可重复结果的人

两个够用的思路：

1. 用 ping 看你到某个地址的往返时间。注意，它只反映你到那个地址的这一段，不等于"经过节点访问目标"的体验。
2. 用 curl 通过本地代理端口请求一个文件，看连接耗时和下载速度。示例如下，其中端口以客户端设置页显示为准，文件地址请换成对方允许测试的公开文件，Windows 的 PowerShell 里请写 `curl.exe`：

```bash
curl -x socks5h://127.0.0.1:<端口> -o /dev/null -s \
  -w "连接 %{time_connect}s  首字节 %{time_starttransfer}s  速度 %{speed_download} B/s\n" \
  <公开文件地址>
```

重复跑几次，比看一次的结果有意义得多。

### 路由追踪：定位"慢在哪一段"

traceroute（Windows 上叫 tracert）和 mtr 会列出数据包经过的每一跳。两个要点：

- 在系统代理模式下，这类探测走的是你本机的直连网络，不经过节点，所以它主要说明"你到节点入口"那一段的路径；是否被 TUN 模式接管因客户端而异，结果要谨慎解读。
- 中间路由器常常对这类探测限速，所以某一跳显示丢包，并不一定影响真实流量。

### IP 质量检测：不测速，测出口

这一类用来看出口 IP 的归属地、所属网络、类型是机房还是住宅，以及域名解析有没有绕开代理，对核对宣传、排查验证码和解锁问题有帮助。原生 IP 的判断见 [原生 IP 机场是什么](/guides/yuansheng-ip-jichang/)，DNS 的检查见 [DNS 泄漏检测](/tutorials/dns-xielou-jiance/)。

## 延迟测试为什么不能全信

延迟测试是最常被拿来当"速度"的数字，也是误读最多的一个：

1. **它测的是一个小请求的耗时，不是带宽。** 延迟低的节点，下载可能很慢；延迟偏高的节点，看视频可能很顺。两者是不同的指标。
2. **测试地址和你真实要访问的站点不在同一条路径上。** 轻量的测试页能通，不代表你常用的网站同样顺畅。
3. **它只是一个瞬间的快照。** 晚高峰和平时可能判若两样，一次读数代表不了一天。
4. **超时不等于节点坏了。** 测试地址不通、订阅过期、系统代理循环，都会表现成"超时"。
5. **同时测一批节点会互相干扰。** 并发发起大量请求时，本机网络和 CPU 都可能引入波动。

所以延迟测试适合回答"通不通"，回答"快不快"要靠后面的方法。

## 为什么测速要重复多次、取居中的结果：往深里讲一层

前面反复说“多测几次”，这里把原因讲透。一次测量的结果，由好几部分叠加而成：你本机当时的负载、Wi-Fi 的信号状态、路径上设备的排队情况、测速服务器自己的繁忙程度，以及节点那一刻有多少人在用。这些因素每次都不一样，所以单次读数天然带着随机波动，一次高或一次低都不说明什么。

取“居中”的结果，而不是平均数或最好的那一次，是因为偶尔出现的极端值会把平均数拉偏。比如五次里有一次刚好碰上本机在同步文件，结果特别差，把它平均进去，整体印象就被带歪了。把几次结果排序后看中间那一个，更接近“通常是什么水平”。记录时把最好和最差的也写上，能帮你看出波动有多大，而波动大本身就是一条重要信息。

再往深一层，是**单线程和多线程的差别**。一般来说，单条连接的吞吐会受往返时间和丢包影响：距离越远、路径上有少量丢包时，单条连接越不容易跑满带宽，而多条连接并发可以绕开一部分限制。所以会出现这样的情况：测速页多线程的结果看着不错，而你在浏览器里下载单个文件却慢得多。这不一定是谁在说谎，只是两种测法在回答不同的问题。基于 UDP 的协议在这方面的表现又和 TCP 不同，具体效果因网络和客户端而异。

最后要说清楚这些原理的边界：它们是通用的网络常识，不是对某个服务的判断。你的运营商、城市、客户端和协议选择都会改变结果，因此最终仍以你自己的多次测试为准，涉及具体服务的条款与限制，请以服务商的官方说明为准。另外，对已经明确不通的节点，不必重复测，把流量留给还有疑问的节点。

## 一次靠谱的机场测速怎么设计：5 个控制变量

用机场测速工具得出可信结果，核心是**控制变量**：每次只改一件事，其余保持不变。

| 变量 | 做法 | 原因 |
|---|---|---|
| 时间段 | 至少测两类：相对空闲时和晚高峰，不同日子重复 | 排除一次性的偶然 |
| 重复次数 | 每个条件至少重复几次，取居中的结果 | 避免被最好或最差的一次带偏 |
| 同条件对比 | 同一设备、同一网络、同一节点、同一目标 | 结果才能互相比较 |
| 排除干扰 | 暂停下载、云同步、视频，必要时改用有线 | 防止本机拖后腿 |
| 记录方式 | 记下时间、节点、网络类型、结果和主观感受 | 之后能复盘、能对比 |

一个够用的记录表，自己照着画就行，不要拿别人的数字来填：

| 日期 | 时段 | 节点名 | 网络类型 | 测试方法 | 结果 | 主观感受 |
|---|---|---|---|---|---|---|
| | | | | | | |

另外，测速本身会消耗流量，并且按倍率扣，倍率怎么算见 [机场流量倍率怎么算](/knowledge/liuliang-beilv-jisuan/)。所以别拿大文件反复测，缩短时长、控制次数，把流量留给真正要验证的节点。

## 按目标选测法：4 种常见场景

| 你的目标 | 推荐组合 |
|---|---|
| 刚导入订阅，想知道哪些节点能用 | 客户端内置延迟测试，挑出不超时的节点，再打开常用网站验证 |
| 想知道看视频、下载够不够 | 网页测速，加上真实场景（视频缓冲、下载一个文件），分两个时段各做几次 |
| 想找出为什么变慢 | 先换节点、换网络类型对比，再做路由追踪看本地到入口的路径，成因排查见 [机场很慢怎么办](/troubleshooting/wanggaofeng-bian-man/) |
| 想核对出口和宣传是否一致 | IP 质量检测，加上 DNS 泄漏检查，对照宣传文案 |

## 6 个常见误读，别踩

| 误读 | 为什么不对 | 更好的做法 |
|---|---|---|
| 延迟低就等于速度快 | 延迟和带宽是两回事 | 延迟看通不通，带宽用下载或网页测速看 |
| 一次测速很高就是稳定 | 一次只是快照 | 多个时段、多天重复 |
| 测速页面的峰值就是日常体验 | 测速页通常多连接并发，日常未必如此 | 再用真实下载和视频场景验证 |
| 别人快我慢，说明被骗了 | 运营商、城市、时段都不同 | 用自己的网络核对，不拿别人的体验当标准 |
| 路由追踪某一跳丢包，线路就有问题 | 中间设备常对探测限速 | 看最终目的地是否有持续丢包 |
| 宣传的"不限速"就是测速结果 | 宣传带宽是标称值，不是端到端体验 | 自己测，并拆解宣传话术，见 [机场虚假宣传怎么识别](/warnings/xujia-xuanchuan-shibie/) |

## 小 D 的一周测速记录：把“感觉慢”变成能复盘的证据（虚构举例）

先说明：下面的人物和经过纯属虚构，只用来演示方法，不对应任何真实用户或服务，也不含任何测试数据，更不代表任何真实结果。

小 D 觉得自己每天晚上看视频总是缓冲，第一反应是“这个节点不行”。但他没有立刻去退款，而是按本文的思路做了一轮记录。第一步，他不开代理测了一次本地宽带，把它当作基线，写在表格的第一行。第二步，他固定了一个节点、一个测试目标，只用网页测速加一次真实的视频缓冲，分别在傍晚前和晚高峰各做几次，每次都记下时间、节点和主观感受。

三天后他回头看这张表，发现两件事。其一，晚高峰时无论走哪个节点，他的手机在客厅角落连 Wi-Fi 的表现都明显更差，而在书房改用有线连接之后，同一个节点的体验好了不少。这说明有相当一部分问题出在本地网络，而不在节点。其二，他换到同一地区的另一个节点后，晚高峰的表现又比原来的更稳定一些，说明原来的节点确实存在一定的拥挤。

于是他做了两件事：把常用设备尽量改成有线或靠近路由器，把默认节点换成表现更好的那个；同时把记录整理后发给客服，写清楚时间、节点和测试方法，客服据此给出了回复。这个例子里没有任何一个“神奇数字”，起作用的只是三样东西：**基线、控制变量、记录**。少了任何一样，小 D 都有可能把本地网络的问题算在节点头上，白白换掉一个其实没问题的服务。

## 测速相关术语速查：10 个词一次对齐

测速的结果能不能读懂，很大程度上取决于这些词有没有弄混：

- **延迟（往返时间）**：一个请求发出到收到回应所用的时间，反映“通不通、跟手不跟手”，不反映一次能搬多少数据。
- **抖动**：延迟忽大忽小的程度。视频会议和在线协作更怕抖动，而不只是平均延迟高。
- **丢包**：数据包在路上丢失的情况。少量丢包也可能拖慢远距离连接的吞吐。
- **带宽与吞吐**：带宽是链路的理论容量，吞吐是你实际拿到的速率，后者受最慢一环限制。
- **基线**：不开代理时测到的本地结果，是你自己的天花板，所有代理测试都要和它对照着看。
- **并发连接**：同一时间的多条连接。测速页常用多连接，日常的单个下载往往不是这样。
- **首字节时间**：请求发出到收到第一个字节的耗时，常用来观察响应是否迟钝，前面 curl 示例里的“首字节”就是它。
- **路由追踪**：列出数据包经过每一跳的工具，适合定位“慢在哪一段”，结果要谨慎解读。
- **流量倍率**：节点实际扣费流量与使用流量的比值，测速也会按它扣流量，见 [流量倍率](/glossary/traffic-multiplier/)。
- **落地节点**：流量最终出口的服务器，IP 质量检测测的就是它那一侧的信息，见 [落地节点](/glossary/exit-node/)。

把这些词放进你的记录表里当列名，下次翻看记录时，就不用再回头猜每一栏代表什么。

## 测完之后怎么用这些结果

测速结果是你自己的证据，可以用在三个地方：

1. **决定是否续费。** 月付到期前，看你记录的几天数据，再决定续不续、换不换。
2. **联系客服。** 把节点、时段、测试方法和多次结果写清楚，附截图，遮住订阅链接。
3. **对比不同服务。** 用同样的条件测不同服务，比看别人评测更接近你的实际情况。

稳定性不是一次测速能下结论的，系统方法见 [稳定机场怎么判断](/guides/wending-jichang-zenme-pan/)。想看公开资料，可以去 [稳定机场推荐](/rankings/stable/)，这里只展示资料基础，不能替代你自己的测试。

今天就能做的事：挑两个节点，选两个时段，每个条件测三次，把结果填进上面的记录表，并在下单前过一遍 [买前自检清单](/tools/airport-checklist/)。一周之后你手里就有了一份属于自己的数据，别当冤大头，也别被一次测速带着走。
